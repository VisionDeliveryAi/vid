# /vid run

One long session runs the tickets to the end. It writes no code, reads none (see "DevAgent's code") and starts no run: DevAgent starts every run, on what ViD asks on the ticket. `checks/round.sh` does what needs no judgement. You do what does: re-planning, answering from the spec, and telling the owner.

**A session that dies stays dead until someone runs `/vid run` again** (the owner types `/vid:vid-run`). Nothing restarts it. The watcher tells the owner, and that is all it does.

## Before any work

**GitHub manual, before anything** (GM-1 S1). When `sh "${CLAUDE_PLUGIN_ROOT}/checks/devagent-start.sh" mode` prints `manual` (in an empty folder, after the restore below), refuse in one line, "this project is in GitHub manual: call /vid next", and record nothing: take no lock and run nothing else. `checks/round.sh` refuses too, as a backstop.

**The spec repository, first** (v0.26.10.26.7, R12). When `.vid/tw/settings` names a `spec-repo:`, run `sh "${CLAUDE_PLUGIN_ROOT}/checks/github.sh" spec-setup --make-only` before the restore and the lock below, which both need it: it makes the spec repository, private, or checks that the one named is private (run it each time: it does nothing more to one that exists), and exports nothing (the first export is `round.sh next`'s, under the lock). Then, unless `sh "${CLAUDE_PLUGIN_ROOT}/checks/devagent-start.sh" mode` prints `auto` (GitHub auto, v0.26.10.28.8 R10: ViD's own DevAgent works on the owner's same `gh` sign-in, and needs no read access given), tell the owner, in one line, to give DevAgent read access to it and to the code repository.

**Ticket mode only.** With an empty folder and a state repository named, first `sh "${CLAUDE_PLUGIN_ROOT}/checks/github.sh" state-restore <state repo>`. It refuses a repository that is not private. Otherwise read `.vid/RUN-STATE.md`: unless it says `mode: tickets`, refuse in one line, "this project is not in ticket mode", and record nothing. A project the old ticket mode planned (0.26.10.28.1, stage 9 R4) — `mode: tickets`, a `.vid/tickets/` folder and no `.vid/tw/settings` — is refused in one line, "This project was planned by the old ticket mode; re-plan it with /vid plan.", and nothing is recorded. Then `sh "${CLAUDE_PLUGIN_ROOT}/checks/github.sh" state-restore`, which brings a folder behind the records up to date and does nothing to one that is current.

**The lock.** `sh "${CLAUDE_PLUGIN_ROOT}/checks/github.sh" lock-take`, the plugin's copy, since the project's may predate this verb until the version check below. If it refuses, say what it said in plain words, write nothing, and end: `run:` belongs to the session that holds the lock. A lock not renewed for 15 minutes may be taken, and the refusal says when.

**The stage event.** `sh checks/event.sh "stage name=run state=start session=$CLAUDE_CODE_SESSION_ID records=29"`, and again whenever a session takes over. Every event this skill names is written with `sh checks/event.sh '<event>'`.

**The internal skill.** Right after the stage event, invoke the `vid-tickets` skill (the Skill tool), and again whenever a session takes over. Claude Code restores after a compaction only the skills that were invoked.

**The run's state.** Rewrite `.vid/RUN-STATE.md`'s keys: `run: active` unless a pause is recorded, or a hold whose stage has closed (`run: stopped owner asked to hold after stage <N>` with its `stage-closed <N>` line: v0.26.10.26.5), `session: $CLAUDE_CODE_SESSION_ID`, `plan: required`, and record `sh checks/event.sh 'run state=active'`. A recorded pause, `run: stopped owner asked to pause`, stays: the session keeps reading and deciding, and `round.sh next` publishes nothing. Rewrite RUN-STATE at each step that changes what it says.

**The refresh** (v0.26.10.26.7, R1), at the start of each `/vid run`: `sh "${CLAUDE_PLUGIN_ROOT}/checks/refresh.sh"`. It prints `refresh: current`, or copies the plugin's `checks/` over `./checks/` and commits it alone (`VID_ROLE=fix`, `Refresh checks/ to VID <version>`). On exit 3 it has listed the local edits a copy overwrites: show the owner that list and ask once; on a yes run it again with `--yes`; on a no, record `run: stopped checks/ needs the refresh`.

**The WSL notice** (0.26.11.1.3, R2), right after the refresh: `sh "${CLAUDE_PLUGIN_ROOT}/checks/lib/wsl.sh" notice`. It prints nothing except once on a native Windows shell with no answer recorded for this PC: there it checks that WSL starts, records the answer and prints one line. Show the owner that line as written, and go on; it asks nothing.

**The watcher.** `sh checks/observe.sh start`, then `sh checks/observe.sh alive`, which exits 0 only when the watcher ticked here within the last 30 minutes. On exit 1, tell the owner what it printed and stop: `run: stopped the watcher is not running`. Its notices are `observe: notice —` lines in the run's heartbeat.

**Your context, the host.** Run `sh checks/brief.sh context` and say its line. The compaction question is a `Q<n>` line (v0.26.10.26.7, R13): unless `.claude/settings.json` sets `autoCompactWindow`, or a `context-window` event records the owner's answer, `queue.sh sync` makes it one and prints `context-window Q<m>` once. Ask it then, in plain words, as that line; the owner's answer is `sh checks/queue.sh answer Q<m> yes|no "<their words>"`, which writes the setting on a yes and the event either way. Never ask it outside the line. Run `sh checks/brief.sh plugins` and give the owner its lines when it names any plugin. It never stops the run.

**The dev side's start** (v0.26.10.28.8, R4), at each `/vid run` start, a resume included, after the refresh and before the loop: `sh "${CLAUDE_PLUGIN_ROOT}/checks/devagent-start.sh"`. In GitHub auto (the owner's setup answer, `github-mode: auto`) it prints the line that makes DevAgent's work folder, the filled-in job note and where to save it, the first way to start DevAgent (`/vid:vid-devagent <job note>` in a new Claude Code conversation in the work folder, R12), then the background line, and the lines for check, list, used and down; in GitHub team, or with no answer, it prints nothing. Show the owner devagent-start.sh's output as it is, unchanged, and go on: never run those lines yourself, never write the note, and never wait for the dev side.

**Reading order, when you plan:** CLAUDE.md, the PRD with its appends, BASELINE, ARCHITECTURE, DECISIONS, the design, INVENTORY.md, STAGES.md.

## The loop

Run `round.sh wait` and `round.sh step` yourself, in the foreground, in this turn; never from a script of your own, nor in the background. Once at each session's start: `sh checks/round.sh step`, then, unless it printed `stop`, `sh checks/round.sh next`. Then, again and again:

1. `sh checks/round.sh wait`, in the foreground, with the Bash tool's timeout at 600000. It blocks with no model, for at most 9 minutes, and prints `new` or `timeout`. A wait never ends your turn: on `timeout`, go to 2.
2. `sh checks/round.sh step`. Read its lines, and act on them:

## DevAgent's code

ViD never writes, reads or runs DevAgent's code (0.26.10.28.4, M5). From DevAgent's side it reads only: the results reports; issues, pull requests, their comments and labels; whether a commit is in the code repository and what it descends from; the deploy reports; and, for the walk, the running product on staging. `.vid/code`, made by `sh checks/github.sh results-fetch`, holds the reports and the commits, with no file of the code: each fetch proves it, and a copy that holds a code file is removed and the fetch refused. ## The only stops

- **Everything left waits on the owner, or `nothing-left`:** `run: waiting` with a `Q<n>` line saying what waits, record `run state=waiting`, `sh checks/github.sh state-save`, `sh checks/github.sh lock-free`, and end. The owner resumes with `/vid:vid-run`.
- **A genuine block, a `stop` line, or a third error running:** `run: stopped <reason>`, the same record, the save, `lock-free`, and end.
- **A lost lock:** `run: stopped lost the lock`, on no write to GitHub. End.

Nothing else ends the session. A long wait is no stop. A question or a held row on one ticket stops that ticket alone.

**You never:** write or change code or tests; read DevAgent's code; start or ask for anything but through the forms of a ticket; answer a product question the spec does not answer; rule a held row without the owner's word (their delegation is their word, recorded `--by delegate`); restart a session; push to the code repository; publish a release.
